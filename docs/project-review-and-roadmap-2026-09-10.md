# AgentGate 正式项目审核与后续路线

审核日期：2026-09-10。范围：当前本地工作树，包括尚未提交的修改。本文是工程审核与路线建议，不是安全认证，也不代表所有功能通过验收。

> 本文是 2026-09-10 的历史审核基线。当前实现、运行态和未完成事项请以根目录 [CONTEXT.md](../CONTEXT.md)、[TODO.md](../TODO.md) 及最新执行报告为准；本文中的“尚未重新执行”不应覆盖后续已经取得的证据。

## 1. 结论与产品定位

项目已有真实的文件检查、审批、隔离、恢复、Worker 执行和审计链路，不只是页面原型。但目前更适合定位为**本地单用户测试版**：异常恢复、Windows 自动验证和可重复交付尚不足以支撑正式稳定版承诺。

建议聚焦为：**面向接入方的本地文件操作权限网关**。外部程序提交结构化动作，AgentGate 判断策略，必要时请求人工批准，再由受限 Worker 执行并留下证据。服务健康监控作为辅助功能，不再作为主线扩大。

必须明确：只有经过网关的动作受控。其他程序直接使用当前 Windows 用户权限操作文件，不会被本项目自动拦截。免密回环部署也不等于能防御同一用户下的恶意进程。不要承诺全机防误删、系统级沙箱或任意 Agent 自动接管。

## 2. 本轮证据范围

- 核查 Worker 执行循环、补报流程、隔离/恢复日志与路径检查、CI、启动和稳定性脚本、依赖声明及现有文档。
- 用现有 Worker Python 环境进行了两个无真实文件操作的最小复现，输出见下文。
- 没有重新执行全量测试、24 小时稳定性测试、渗透测试或从零部署。因此历史通过数字不能作为本轮验收结果。
- 未修改业务代码、运行配置或用户文件；没有提交或推送 Git。

## 3. 优先问题

### R1：永久失败的补报会阻塞后续任务（P1，已复现）

位置：`apps/worker/agentgate_worker/main.py:80`、`apps/worker/agentgate_worker/client.py:549`。

执行循环先补报再领取任务。任意补报请求抛出协议异常，当前循环就不会领取任务；日志只有上报成功后才标记已报告。永久拒绝若未被其他机制解决，会持续重试。心跳与任务进展是分离的，单看在线状态不能证明 Worker 可工作。

本轮使用模拟客户端令补报抛出 `WorkerProtocolError('403')`，实际输出：`claim_after_report_failure=0`。

处理方向：保留服务端结构化错误码，区分瞬时失败、凭据失效、单任务终态冲突；提供可审计的对账状态。不能简单把所有 403 忽略或删除日志；全局凭据失效应停止领取，单任务终态冲突则应进入明确的人工/自动对账流程。

验收：制造过期任务、撤销凭据、网络中断和服务端重启，验证无无限无效重试、无重复文件执行、无静默丢弃证据；状态页显示阻塞原因。

### R2：恢复中断可能漏报（P1，已复现）

位置：`apps/worker/agentgate_worker/quarantine.py:290`。

恢复日志和隔离日志按同一个 `action_id` 汇总。历史 `completed` 会抵消后续 `restore_prepared`，即使没有 `restore_completed`。

本轮输入同一动作的 `prepared → completed → restore_prepared` 三条记录，实际输出：`incomplete_restore_notices=[]`。这是恢复告警遗漏的证据，不等于已证明发生文件丢失。

处理方向：按操作类型与操作实例标识分别配对，明确恢复尝试的状态机。文件移动前后任一点退出，都应能识别真实文件位置并进入恢复或人工复核流程。

验收：对隔离和恢复的每个持久化/移动边界做故障注入；不得把未完成操作判成已完成，不覆盖已有目标，不擅自重复移动。

### R3：路径边界仍有需要验证的空隙（P1，静态风险）

位置：`apps/worker/agentgate_worker/quarantine.py:110`、`:180`、`:248`。

恢复目标检查遍历相对路径的父级，但该函数没有重新检查根目录本身；隔离路径创建和恢复源检查也未在这些路径上完整验证所有祖先。路径检查与实际移动分离，存在检查后目录被替换的时间窗口。

成立前提：其他本地主体能更改相关目录结构。尚未进行 Windows junction 并发替换复现，不能将静态风险写成已证实越界攻击。

处理方向：先明确可信目录、ACL 和攻击者权限；补齐根及祖先重解析点验证；评估句柄式校验/移动或受控目录权限方案。若暂不提供对抗同用户恶意进程的保证，文档必须明确限制，不能仅凭路径字符串检查宣称系统级隔离。

验收：覆盖根目录替换、祖先 junction、目标冲突、跨卷、长路径、大小写、并发改名及重复请求。仅在专用临时工作区测试。

### R4：CI 未覆盖核心部署平台（P1，配置已确认）

位置：`.github/workflows/ci.yml:9`。

当前工作流只有 Ubuntu API/Web 验证，未安装或测试原生 Worker，也未配置真实 PostgreSQL 服务测试任务。Windows 文件和凭据行为不能依赖 Linux 测试替代。

验收：增加 Windows Worker 测试及 PowerShell 合约任务、真实 PostgreSQL 迁移与事务测试；对跳过项给出原因和替代证据。分支合并前要求关键任务成功。

### R5：启动失败可能被旧服务掩盖（P2，代码路径已确认）

位置：`scripts/start-local.ps1:47`。

Compose 构建/启动后没有立即检查退出码，只等待 API `/health`。如果新构建失败而旧 API 仍健康，脚本可能输出启动成功；Web、scheduler、control-worker 未在此处逐个就绪验证。

验收：构建失败、端口占用、Web 启动失败、数据库迁移失败都必须返回非零；成功输出必须对应预期服务和版本，不只是已有 API 活着。保留用户端口、模型与认证配置。

### R6：稳定性统计不足以证明连续运行（P2，代码已确认）

位置：`scripts/soak-worker.ps1:58`、`:119`。

脚本以墙上时间截止，未计算有效采样覆盖率或最大采样间隔；部分异常结果仍返回 0。还需检查目标最后探测时间，防止历史 healthy 值被当成持续成功。

历史 1227 次采样有多次长间隔，因此不能表述为通过连续 24 小时验收。睡眠是可能解释，不是已证明根因。

验收：分别输出通过、业务失败、环境中断、证据不足；记录单调时钟、实际间隔和探测新鲜度。建议正常场景最大间隔不超过约定采样周期的 3 倍，覆盖率至少 95%；阈值须在运行前固定，而不是看到结果后修改。

### R7：交付和依赖复现能力不足（P2）

API Python 依赖使用版本范围，已跟踪锁文件仅发现 Web 的 `package-lock.json`。一次本地依赖扫描不能代表以后构建的容器或其他机器。

验收：API/Worker 固定解析结果并建立升级流程；CI 检查实际交付依赖；产物标注版本和提交号。明确支持的 Windows、Python、Docker 环境，在干净机器执行安装、升级和回滚演练。

## 4. 文档和使用体验

1. README 主线只保留用途、边界、快速安装、一次真实操作、故障入口；长篇协议细节放入专题文档。
2. 示例状态工具与真实文件执行必须分开标注。不能让用户以为示例 `restart_service` 已经重启 Windows 服务。
3. 操作页统一显示：策略决定、审批状态、执行状态、结果上报状态；“在线”不等于“执行正常”。
4. 错误提示给出原因和安全的下一步，保留可用于审计的错误码；禁止直接显示密钥或完整敏感路径。
5. 初始化和首次工作区登记应能完成一个正常业务流程，不要求用户理解 bootstrap、journal 等内部术语；高级配置仍可展开查看。
6. 旧报告中的测试结果保留日期。父子 Python 进程不能直接认定为重复 Worker 实例，稳定性长采样空洞不能记为连续成功。

## 5. 后续路线与工程量

以下为单人熟悉代码、优先 Windows 本地单用户场景的粗估；单位为有效工程日，不是承诺工期。遇到 Windows 文件句柄方案或数据库兼容性问题，应重新估算。

| 阶段 | 内容 | 工程量 | 出口条件 |
| --- | --- | --- | --- |
| A：可靠性收口 | R1 补报对账、R2 恢复状态机、R3 路径边界验证；先写失败回归再修复 | 5–9 日 | 故障注入无重复执行、无漏报中断、无已知越界缺口；限制写清 |
| B：可重复交付 | Windows/PostgreSQL CI、依赖固定、启动失败检测、版本信息、数据恢复演练 | 4–7 日 | 新机器按文档安装成功；升级失败可恢复；CI 覆盖关键平台 |
| C：真实接入与简化 | 一个外部 Agent/普通脚本通过正式 API 提交文件动作；整理权限配置、审批和失败体验 | 4–6 日 | 不依赖内部测试入口完成检查、拒绝、审批、隔离、恢复和审计关联 |
| D：发布验收 | 连续运行证据、异常重启/断网、文档走查、发布说明 | 2–4 日，另加至少 24 小时观察 | 所有发布门槛有可追溯结果，没有未解释失败 |

建议总预算约 15–26 个有效工程日。先完成 A，再根据实际发现调整 B–D，避免一次铺开新功能。

### A 阶段具体顺序

1. 固定两个最小复现为回归测试，记录现有失败。
2. 定义任务补报错误分类和服务端终态对账协议，避免客户端单方面判定成功。
3. 为隔离与恢复定义独立操作实例和持久化配对规则。
4. 补故障注入和 Windows 路径边界用例，再选择最小安全实现。
5. 回归检查审批拒绝、幂等与令牌范围没有因恢复逻辑而放宽。

### B 阶段必须包含的恢复演练

数据库备份不是全部备份：还要考虑隔离文件、Worker journal、配置及凭据的恢复关系。凭据受 DPAPI 保护，不能假定直接复制到另一台机器即可工作。验证恢复后旧任务是否会重复执行；跨机器应有重新注册和状态对账流程。备份不能把明文密钥提交进仓库。

### C 阶段的最小真实业务

选择“整理项目生成文件”的外部调用脚本：仅能请求已登记工作区内指定文件动作；普通文件进入审批，受保护文件拒绝；批准后隔离而非永久删除，随后可恢复。请求方用受限客户端凭据，不持有管理员凭据。展示是用户使用正常功能，不在产品首页写“面试演示”。

这个用例验收的是接入协议和执行控制，不是假定脚本本身已失去直接访问本地文件的权限。若要强制防绕过，需要另立权限隔离项目，不能包装成已有能力。

## 6. 正式本地版本发布门槛

- R1–R4 已解决或对不支持的安全场景作出明确、可测试的范围限制；不得遗留已知数据一致性缺陷。
- Windows 文件链路、PostgreSQL 事务/迁移、API/Web 和真实接入验收有本次提交对应的记录。
- 重复请求、审批过期/拒绝、网络失败、进程中断和恢复冲突均有确定结果。
- 一次从零安装、一次升级与一次备份恢复成功；失败时能定位且不覆盖用户配置。
- 稳定性报告含采样覆盖率、间隔、新鲜度、失败记录及明确结论，不将证据不足记作通过。
- README 能让未参与开发者完成首次实际操作；能力边界、免密风险和排障方法一致。
- 版本标签、变更说明、许可证选择和已知限制明确；公开仓库发布前检查密钥和私人数据。

## 7. 暂不建议投入

暂不做 Windows 驱动级拦截、全盘扫描、任意 Shell、远程执行、多租户、Kubernetes、多模型编排或再次大改视觉风格。这些不是当前最短的实用化路径。

项目展示价值应来自：真实权限链路、故障恢复证据、明确安全边界与可重复交付，而不是功能数量。下一步最值得执行的是 A 阶段的两个已复现缺陷及其回归测试。
